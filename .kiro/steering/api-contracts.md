# API Contracts

Defines what the frontend expects from the backend. These shapes are the shared contract
that both sides build against: the frontend service layer consumes them and the backend
produces them. Frontend and backend are developed in parallel, so this contract is the
integration point. Treat these as agreed shapes; changes must be coordinated across both
teams.

Notes:
- Data persistence runs through Supabase (no Supabase Auth). AI orchestration runs through
  the FastAPI + LangGraph backend. The frontend does not care which is which beyond the
  service interface.
- All shapes below are conceptual (field lists), not implementation code. IDs are UUID
  strings; timestamps are ISO 8601 strings.

## Guest Identity Flow (No Auth)

There is no sign-up / sign-in. Identity is room-scoped: `room + normalized display name →
room member` (see `supabase-architecture.md`).
- Join input: `{ roomCode, displayName }`.
- Join result: `{ room, member, guest, character, travelPreferences, trip }` (shapes below). If a
  member with the same normalized display name (trimmed, case-insensitive) already exists in
  the room, that member is resumed instead of a new one being created. See "HTTP API" for
  the exact requests.
- All ids are generated by the database/backend — the client never creates identity UUIDs.
- The client may cache `roomId`, `memberId`, `guestId`, and `displayName` locally for
  convenience; this is not authentication and there are no tokens, passwords, or auth
  errors.
- Subsequent calls carry the `memberId`, which is self-asserted (guest/demo trust model).
- "User" in the shapes below means this room member.

Shapes:
- Guest: `{ id, displayName, avatarUrl? }`.
- Party room: `{ id, roomCode, name, status: "active" | "finalised" | "cancelled",
  planningStage, demoScenario?, demoStart? }`.
  `demoScenario` is `"vietnam-five-days"` for prepared rooms, otherwise null/absent.
  This persisted scenario key is retained for compatibility; new prepared
  recommendations offer Da Nang (Vietnam), Bali (Indonesia) and Phuket (Thailand),
  with destination-specific sample flights and itineraries.
  `demoStart` is the shared YYYY-MM-DD departure date, set at room creation using
  Singapore time plus seven days. New rooms created by the reserved lobby name
  `DemoAlice` enter this scenario; only `DemoBob` may join its second seat. These
  names use the existing normalized display-name identity and are not credentials.
  The demo uses normal FastAPI writes and Supabase Realtime, but both agent execution
  entry points bypass Gemini and external tools. See [the demo guide](../../docs/PREPARED_DEMO.md)
  for fixed profiles, sample recommendations, scripted refinement and deployment order.
- Room member: `{ id, roomId, guestId, displayName, role: "owner" | "member", stageReady }`.
  `displayName` is the name as first entered, even when resumed with different casing.
  `stageReady` is `true` once the member has done their part in the current stage (see
  "Stage readiness").
- Character: `{ id, memberId, appearance, spriteKey? }` — `appearance` is a free-form
  object.
- Travel preferences: `{ id, memberId, availableDates, destinations, travelStyle?,
  budget?, interests, activities, hardConstraints, origin?, submittedAt? }` — list fields
  are arrays (empty when new); `availableDates` is a list of `{ start, end }` date ranges;
  `budget` is SGD 100–50,000 per person for the whole trip (including flights) or null;
  `origin` is the departure city or
  IATA code for flight search; `submittedAt` is null until the member first saves.
- Trip: `{ id, roomId, title, summary?, status }` — one per room, created with it.
  `status` is the trip state (see "Stage & State"); the `tripId` is what AI-run and
  itinerary endpoints take.

## HTTP API (FastAPI)

The backend endpoints the frontend service layer calls. This section is the source of
truth for paths, request bodies, status codes, and errors. The running backend also serves
interactive docs at `{API_BASE_URL}/docs` (generated from the code); if they disagree with
this section, treat it as a bug and fix one side.

Conventions:
- Base URL: `NEXT_PUBLIC_API_BASE_URL` (local default `http://localhost:8000`).
- JSON bodies, camelCase fields, `Content-Type: application/json`.
- No auth headers. Identity comes from the room code + display name (see above).
- Fields marked `?` may be `null` in responses.

### `GET /health`

Liveness check. `200` → `{ "status": "ok" }`.

### `POST /rooms` — create a room

Creates the room, a unique 6-character room code, and the caller as the `owner` member,
with an empty character and preferences, in one transaction.

Request:

```json
{ "name": "Adventure Club Trip", "ownerDisplayName": "Gerald" }
```

- `name`: 1–100 characters, not blank.
- `ownerDisplayName`: 1–50 characters, not blank.

`200` response (same shape for both room endpoints):

```json
{
  "room": { "id": "…", "roomCode": "1HSM6S", "name": "Adventure Club Trip",
            "status": "active", "planningStage": "setup" },
  "member": { "id": "…", "roomId": "…", "guestId": "…",
              "displayName": "Gerald", "role": "owner", "stageReady": false },
  "guest": { "id": "…", "displayName": "Gerald", "avatarUrl": null },
  "character": { "id": "…", "memberId": "…", "appearance": {}, "spriteKey": null },
  "travelPreferences": { "id": "…", "memberId": "…", "availableDates": [],
                         "destinations": [], "travelStyle": null, "budget": null,
                         "interests": [], "activities": [], "hardConstraints": [],
                         "origin": null, "submittedAt": null },
  "trip": { "id": "…", "roomId": "…", "title": "Adventure Club Trip", "summary": null,
            "status": "trip_created" }
}
```

Errors: `422 VALIDATION_ERROR`, `500 ROOM_CODE_EXHAUSTED`, `503 DATABASE_ERROR`.

### `POST /rooms/{roomCode}/join` — join or resume

- `roomCode`: 4–12 uppercase letters or digits (e.g. `ABC123`). Anything else is rejected
  with `422` before the room is looked up, so uppercase user input first.
- If the room already has a member whose name matches ignoring case and surrounding
  spaces (`"gerald"` matches `"Gerald"`), that member and their records are returned
  unchanged. Otherwise a new `member`-role member is created.

Request:

```json
{ "displayName": "Priya" }
```

- `displayName`: 1–50 characters, not blank.

`200` response: same shape as `POST /rooms`. On resume, `character` and
`travelPreferences` may be `null` if those records do not exist. When a new member makes the
room 2+ members, `trip.status` advances to `group_formed`.

Errors: `404 ROOM_NOT_FOUND`, `409 MEMBER_ALREADY_EXISTS` (two people joined with the same
name at the same moment — retrying the join resumes that member), `422 VALIDATION_ERROR`,
`503 DATABASE_ERROR`.

### `PUT /rooms/{roomCode}/members/{memberId}/preferences` — save preferences and character

Replaces the member's preferences, and optionally their pixel character, in one call. All
preference fields are optional; anything omitted is saved as empty (`[]` or `null`), so
always send the full set. `character` is different: omit it to leave the character as it
is, or send it to replace it.

```json
{
  "availableDates": [{ "start": "2026-12-20", "end": "2026-12-27" }],
  "destinations": ["Tokyo", "Seoul"],
  "travelStyle": "relaxed",
  "budget": 1500,
  "interests": ["food", "museums"],
  "activities": [{ "name": "hiking", "priority": "must_have" }, { "name": "spa", "priority": "optional" }],
  "hardConstraints": ["no red-eye flights"],
  "origin": "SIN",
  "character": {
    "appearance": { "outfit": "explorer", "palette": "forest", "accessory": "backpack" },
    "spriteKey": "explorer-01"
  }
}
```

- `availableDates`: up to 20 inclusive date ranges `{ start, end }` (ISO `YYYY-MM-DD`,
  `end` ≥ `start`). The AI plans for the dates where every member's ranges overlap.
- `budget`: SGD per person for the **whole trip, including flights**, from **100 to
  50,000**, or `null` (not sure). Anything outside that range is refused with
  `422 INVALID_BUDGET` and a message to show next to the field. The lowest amount in the
  party becomes its hard limit; the budget level (Low/Medium/High, sent as
  `character.appearance.budgetTier`) sets the spending style. See "Trip budget".
- `travelStyle` (≤ 50 chars) and `origin` (≤ 100 chars): blank becomes `null`.
- `activities`: objects with `"priority": "must_have"` (or `"required": true`) mark
  must-haves; any other priority is treated as optional.
- `origin`: also copied into `hardConstraints` as `{ "type": "departure_origin", "value": … }`,
  which is where the AI's flight search currently reads it. Don't send that entry yourself.

- `character.appearance`: free-form object from the character creator (up to 50 keys).
  `character.spriteKey`: which sprite to draw (≤ 100 chars), or `null` for the default.

`200` response: `{ "travelPreferences": { … }, "character": { … }, "trip": { … } }`
(`character` is `null` only if the member has none). When this was the last
member to save, `trip.status` is now `preferences_collected` (stage `discover`), and the
party can start a `discovery` run.

Errors: `404 ROOM_NOT_FOUND`, `422 MEMBER_NOT_RESOLVED` (member is not in this room),
`422 INVALID_BUDGET` (budget outside SGD 100–50,000; nothing is saved),
`422 VALIDATION_ERROR`, `503 DATABASE_ERROR`.

### `POST /votes/{voteSessionId}/cast` — cast or change a vote

Vote sessions are opened by the AI (a `discovery` run opens the destination vote, a
`logistics` run the flight vote) and arrive as `kind: "vote"` messages; the frontend never
opens one. Voting again replaces the member's previous choice.

```json
{ "memberId": "…", "optionId": "opt-tokyo" }
```

`200` response:

```json
{ "voteSessionId": "…", "memberId": "…", "optionId": "opt-tokyo", "sessionStatus": "open",
  "tiePending": false }
```

When the last member votes, the session resolves in the same call:
- **Clear winner:** the session closes (`sessionStatus: "closed"`), the winner is saved as
  the destination or flight selection, and `trip.status` advances to `destination_selected`
  or `flight_selected`.
- **Tie:** nothing is locked. The session stays open with `tiePending: true` (see "Ties"
  below), a `tiebreak` AI run starts automatically, and the room owner picks the winner.

Errors: `404 VOTE_SESSION_NOT_FOUND`, `422 VOTE_SESSION_CLOSED`, `422 VOTE_TIE_PENDING` (the
vote is tied and waiting for the owner), `422 MEMBER_NOT_RESOLVED`
(member is not in the vote's room), `422 VALIDATION_ERROR` (including an `optionId` that is
not one of the session's options), `503 DATABASE_ERROR`.

### `POST /votes/{voteSessionId}/close` — close a vote early (owner only)

```json
{ "memberId": "…" }
```

Closes with the votes cast so far. `200` response:

```json
{
  "voteSessionId": "…",
  "category": "destination",
  "tiePending": false,
  "winningOption": { "id": "opt-tokyo", "title": "Tokyo" },
  "tie": null,
  "selectionId": "…"
}
```

If the votes so far are tied, nothing is locked: `tiePending` is `true`, `winningOption` and
`selectionId` are `null`, `tie` is `{ "tiedOptionIds": [...], "tiedCount": 1 }`, and the
tiebreak flow below starts.

Errors: as for cast; `422 MEMBER_NOT_RESOLVED` also means "not the room owner".

### Ties: AI advice, leader decides (destination and flight votes)

When a vote ties:

1. **The session waits.** It stays `open` with `tie_pending: true`, `tie_option_ids` (the
   tied option ids) and `category` (`"destination"` or `"flight"`); these fields stream
   over Realtime on `vote_sessions`. No more votes are accepted (`422 VOTE_TIE_PENDING`).
2. **The guide announces it** with a `summary` message: `title: "It's a tie!"`,
   `details: { tie_pending: true, vote_session_id, tied_ids, tied_count, category }`.
3. **The guide advises the owner.** A `tiebreak` run starts automatically (you can also
   retry it with `POST /trips/{tripId}/runs`, `runType: "tiebreak"`). It posts one
   `summary` message:

```json
{
  "kind": "summary",
  "content": {
    "title": "A tie for the leader to break",
    "text": "Scoot is within budget for everyone; ANA is more comfortable…",
    "stage": "LOGISTICS",
    "category": "flight_tiebreak",
    "vote_session_id": "…",
    "options": [ { "id": "f1", "label": "Scoot TR804" }, { "id": "f2", "label": "ANA NH804" } ],
    "advice": "Scoot is within budget for everyone; ANA is more comfortable…",
    "recommended_option_id": "f1",
    "items": [
      {
        "id": "f1", "title": "Scoot TR804", "label": "Scoot TR804",
        "description": "SIN to NRT, direct, 6h 25m, SGD 1,136.",
        "votes": ["Gerald"],
        "score": 84,
        "whyThisFits": "Cheapest and direct.",
        "tags": ["Budget", "Direct", "Evening arrival"],
        "tradeOff": "No checked bag included.",
        "details": "Scoot TR804, SIN to NRT. Departs … SGD 1,136 per person, round trip.",
        "facts": { "price": 1136.5, "stops": 0, "duration_minutes": 385 },
        "memberFit": [
          { "memberId": "…", "displayName": "Gerald", "score": 92, "reason": "Fits Gerald's budget." },
          { "memberId": "…", "displayName": "Priya", "score": 70, "reason": "Fine, but Priya preferred ANA." }
        ]
      },
      { "id": "f2", "title": "ANA NH804", "votes": ["Priya"], "score": 61, "…": "…" }
    ]
  }
}
```

   - `category` is `"destination_tiebreak"` or `"flight_tiebreak"`.
   - Each item uses the **same card keys as recommendation items** (`score`,
     `whyThisFits`, `tags`, `tradeOff`, `details`; see "Recommendation Response
     Structure"), so the tiebreak panel can reuse the recommendation card. Here `score`
     is the fit re-judged for this tie, with the party's votes and each member's own
     preferences in view.
   - `memberFit` gives each member's own 0–100 score and a one-line reason, based on that
     member's budget, interests, activities, wish-list destinations and constraints. Show
     it so the leader can see who each option suits and why.
   - `votes` lists who voted for the option; `facts` holds the raw comparable values
     (flight price/stops/duration/times, or the destination's original card values).
   - `recommended_option_id` is the highest-scoring option. It is only a suggestion and
     may be absent if the options score the same.
   - Without the LLM the guide still posts scores in the same shape, using a simple rule:
     each member starts at 50, +25 if they voted for it, then +25 for a wish-list
     destination or a flight within their budget (−25 if over it); the party score is the
     average. `tags` and `tradeOff` then come from the original recommendation card (may
     be empty).
4. **The owner decides** with `POST /votes/{voteSessionId}/break-tie`.

### `POST /votes/{voteSessionId}/break-tie` — pick the winner of a tie (owner only)

```json
{ "memberId": "…", "optionId": "f1" }
```

`optionId` must be one of `tie_option_ids`. The pick locks exactly like a normal winner:
the selection is saved (with the option's full details), the session closes, and the trip
advances to `destination_selected` or `flight_selected`. The guide posts a short "the
leader has decided" summary. `200` response: the same shape as `close`, with `tie` set.

Errors: `404 VOTE_SESSION_NOT_FOUND`, `422 VOTE_SESSION_CLOSED`, `422 MEMBER_NOT_RESOLVED`
(not the room owner), `422 VALIDATION_ERROR` (the vote is not tied, or `optionId` is not a
tied option), `503 DATABASE_ERROR`.

### `POST /trips/{tripId}/runs` — start an AI run

```json
{ "runType": "discovery", "memberId": "…", "idempotencyKey": "discover-1" }
```

- `runType`: `"discovery" | "logistics" | "itinerary" | "refinement" | "tiebreak"`
  (`tiebreak` normally starts by itself when a vote ties; see "Ties").
- `idempotencyKey` (optional, 1–200 chars): send the same key on a retry to get the same
  run back. The same key always returns that run, **even a failed one**, so a "Try
  again" after a failure must send a new key (the frontend uses
  `discovery-{tripId}-retry-{timestamp}`).

`202` response: the run (see "AI Runs"), normally with `status: "pending"`. The AI works in
the background, which can take a minute or more. If a run of this type is already in
progress for the trip, or the key was used before, that existing run is returned instead.

Follow progress through Realtime rather than waiting on the request: the AI posts a
`text` message with `progress: true` when it starts, then its output (recommendation + vote,
or a new itinerary version), or a `text` message if it failed. Poll `GET /runs/{runId}` if
you need the final status.

Errors: `404 TRIP_NOT_FOUND`, `409 IDEMPOTENCY_KEY_CONFLICT` (key already used for a
different trip or run type), `422 MEMBER_NOT_RESOLVED`, `422 INVALID_IDEMPOTENCY_KEY`,
`422 VALIDATION_ERROR`, `503 DATABASE_ERROR`. Failures inside the AI run itself do not
fail this request; they show up as the run's `status: "failed"` with a safe `error`.

### `GET /runs/{runId}` — AI run status

`200` response: the run. Errors: `404 RUN_NOT_FOUND`, `503 DATABASE_ERROR`.

### `GET /trips/{tripId}/runs/latest` — what the guide is doing now

Query: `runType` (optional): `discovery`, `logistics`, `itinerary`, `refinement` or
`tiebreak`. Returns the trip's most recent run of that type, or `null` before any run:

```json
{ "id": "…", "runType": "logistics", "status": "running",
  "phase": "searching_flights", "elapsedSeconds": 7 }
```

- `phase` is the real step the run is on, or the step it failed on:
  `reading_party`, `asking_guide`, `searching_flights`, `checking_budget`,
  `checking_answer`, `drafting_days`, `weighing_feedback`, `weighing_options`, `posting`
  (`null` until the first step). The frontend maps these to in-world lines
  (`frontend/src/features/party-lobby/lib/guidePhases.ts`).
- Poll every ~2s while the guide is working (every ~6s once finished, to catch a
  retry). `agent_runs` itself stays backend-only.
- A `failed` run whose `phase` is `searching_flights` means the flight provider was
  unavailable (e.g. out of monthly searches).

Errors: `404 TRIP_NOT_FOUND`, `503 DATABASE_ERROR`.

### `GET /trips/{tripId}/itinerary/versions` — list itinerary versions

`200` response: every version, oldest first (see "Itinerary Versioning"):

```json
[
  { "id": "…", "tripId": "…", "version": 1, "source": "build", "status": "proposed",
    "itinerary": { … }, "changeSummary": null }
]
```

Errors: `404 TRIP_NOT_FOUND`, `503 DATABASE_ERROR`.

### `POST /trips/{tripId}/feedback` — give feedback on the itinerary (REFINE)

A member comments on the version under review (the latest `proposed` one).

```json
{
  "memberId": "…",
  "itineraryVersionId": "…",
  "target": { "day": 2, "itemId": "d2-i3" },
  "comment": "Swap the museum for a street-food market."
}
```

- `target`: must include `day` (≥ 1) and/or `itemId` (an activity's `id` from the
  itinerary), because the AI revises the plan day by day and activity by activity.
  `section` is optional extra context. Feedback naming neither is rejected with `422`.
- `comment`: 1–1000 characters, not blank.

`201` response: `{ "feedback": { id, tripId, itineraryVersionId, memberId, target, comment,
status: "open" }, "trip": { … } }`. The member is marked ready for this round and the trip
moves to `feedback_collected`. To act on the feedback, start a `refinement` run
(`POST /trips/{tripId}/runs`); it proposes a new version and marks the feedback
`addressed`.

Errors: `404 TRIP_NOT_FOUND`, `404 ITINERARY_VERSION_NOT_FOUND`, `409 VERSION_NOT_PROPOSED`
(the version is superseded, approved, or rejected), `422 MEMBER_NOT_RESOLVED`,
`422 VALIDATION_ERROR`, `503 DATABASE_ERROR`.

### `POST /trips/{tripId}/itinerary/versions/{versionId}/decision` — approve or reject (owner only)

```json
{ "memberId": "…", "decision": "approve" }
```

- Only the room owner can decide, and only on the version under review.
- `approve`: the version becomes `approved`, the trip moves to `trip_approved` (stage
  `wrap`), and the guide posts its final `summary` message.
- `reject`: the version becomes `rejected`; the party can give more feedback and run
  another refinement.

`200` response: `{ "version": { … }, "trip": { … } }`.

Errors: `404 TRIP_NOT_FOUND`, `404 ITINERARY_VERSION_NOT_FOUND`, `409 VERSION_NOT_PROPOSED`,
`409 DUPLICATE_APPROVAL` (another version is already approved), `422 MEMBER_NOT_RESOLVED`
(not the owner), `422 VALIDATION_ERROR`, `503 DATABASE_ERROR`.

### `GET /trips/{tripId}/budget` — the party's trip budget (sidebar card)

Per-person budget, in SGD. Re-fetch when a member saves preferences, a vote locks a
destination or flight, or an itinerary version arrives (the frontend's budget service
does this from Realtime changes on `room_members`, `selections` and `itinerary_versions`).

```json
{
  "currency": "SGD",
  "days": 5,
  "isHardLimit": true,
  "limit": 1200,
  "limitSetBy": "Priya",
  "level": "low",
  "levelCount": 1,
  "dailyRange": { "low": 50, "high": 120, "typical": 80 },
  "levelEstimate": 400,
  "estimates": { "stay": 250, "flight": 320, "activities": 75.5, "total": 645.5 },
  "remaining": 554.5,
  "isOverBudget": false,
  "members": [
    { "memberId": "…", "displayName": "Priya", "amount": 1200, "level": "low" },
    { "memberId": "…", "displayName": "Gerald", "amount": null, "level": "medium" }
  ]
}
```

- `days`: the trip's own length, from the locked flight's dates, else the chosen
  destination's `tripDays`. `null` until a destination is chosen (so is `levelEstimate`).
- `isHardLimit` / `limit` / `limitSetBy`: the lowest typed amount and who typed it. When
  nobody typed one, `isHardLimit` is `false`, `limit` and `remaining` are `null`, and the
  level is a guide only.
- `level` / `dailyRange` / `levelEstimate`: the lowest budget level anyone picked, its
  daily range per person excluding flights (Low 50–120, Medium 120–250, High 250+;
  `high` is `null` when open-ended), and the typical spend for the trip at that level.
- `estimates`: what the trip is expected to cost so far. `stay` = the locked
  destination's `estimatedDailyCostSgd` × `days` (an AI estimate), `flight` = the locked
  flight's price, `activities` = the sum of costed itinerary items (approved version, else
  the latest). Each is `null` until known; `total` sums the known parts.
- `remaining` = `limit − estimates.total`; `isOverBudget` when it is negative.

How the stages use the budget: DISCOVER drops suggestions whose stay alone exceeds the
hard limit (or labels them in `tradeOff` when only a level is set); LOGISTICS searches on
the trip's dates and drops flights above what the limit leaves after the stay, but if that
leaves none it still shows the cheapest ones, tagged "Over budget" with how far over in
`tradeOff`, so the party can always move on; BUILD checks costed activities against what
is left after the flight and the stay. A missing estimate never excludes anything.

Errors: `404 TRIP_NOT_FOUND`, `503 DATABASE_ERROR`.

### `GET /trips/{tripId}/trip-dates` — the trip's dates (sidebar card)

The trip's own length and dates (not the party's availability), plus what they may be
changed to. Re-fetch on Realtime changes to the room's `selections`.

```json
{
  "destination": "Penang, Malaysia",
  "tripDays": 4,
  "tripStart": "2026-10-15",
  "tripEnd": "2026-10-18",
  "whyThisLong": "Four days covers George Town and the hill.",
  "windows": [{ "start": "2026-10-12", "end": "2026-11-10" }],
  "minDays": 2,
  "maxDays": 14,
  "dailyCostSgd": 32,
  "budgetLimit": 1200,
  "canChange": true,
  "lockedReason": null
}
```

- `tripDays` / `tripStart` / `tripEnd` / `whyThisLong` are `null` until a destination is
  chosen. `whyThisLong` is `"Set by the party leader."` after a change.
- `windows`: the date ranges when the whole party is free; the trip must sit inside one.
- `minDays` / `maxDays`: 2–14, capped by the longest window.
- `dailyCostSgd` / `budgetLimit`: for previewing the stay cost against the hard limit;
  either may be `null`.
- `canChange` is `false` before a destination is chosen and after a flight is locked;
  `lockedReason` then says why. Only the room owner may change (the UI checks the role).

Errors: `404 TRIP_NOT_FOUND`, `503 DATABASE_ERROR`.

### `PUT /trips/{tripId}/trip-dates` — change the trip's dates (owner only)

```json
{ "memberId": "…", "days": 6, "start": "2026-10-20" }
```

Returns the same body as the `GET`. The end date is `start + days − 1`. On success the
destination selection carries the new plan, any open flight vote is closed (its flights
were for the old dates) and every member's `stageReady` is reset, and the guide posts a
note. The caller then starts a fresh `logistics` run (a new idempotency key) to search
flights for the new dates. A flight vote that is `closed` with no flight selection means
"dates changed, search again": the frontend hides those flights.

Errors: `422 MEMBER_NOT_RESOLVED` (not the owner), `404 NOT_FOUND` (no destination chosen yet),
`422 INVALID_TRIP_DATES` (length outside `minDays`–`maxDays`, start in the past, or
outside every window; the message is safe to show), `409 TRIP_DATES_LOCKED` (flight
already locked, or a flight search is running; the message is safe to show),
`404 TRIP_NOT_FOUND`, `503 DATABASE_ERROR`.

### `POST /trips/{tripId}/export` — the final, shareable trip (WRAP)

No body. `200` response:

```json
{
  "trip": { … },
  "room": { … },
  "itinerary": { "id": "…", "version": 2, "status": "approved", "itinerary": { … }, … },
  "destination": { "id": "tokyo", "title": "Tokyo", … },
  "flight": { "title": "Scoot TR804", "depart_at": "…", "return_at": "…", "price": 1136.5, … },
  "party": [ { "displayName": "Gerald", "role": "owner", "spriteKey": "explorer-01" } ]
}
```

`destination` and `flight` are the locked selections' details (or `null`). The first call
moves the trip to `trip_exported`; calling again returns the same trip.

Errors: `404 TRIP_NOT_FOUND`, `404 NO_APPROVED_ITINERARY`, `503 DATABASE_ERROR`.

### `POST /rooms/{roomCode}/messages` — send a chat message

```json
{ "memberId": "…", "text": "Ramen first, then the onsen?" }
```

- `text`: 1–1000 characters, not blank.

`201` response: the message envelope (see "Chat Message Flow"):
`{ id, roomId, createdAt, senderType: "user", senderId, kind: "text", content: { text } }`.
Everyone in the room receives it live over Realtime (`messages`), in the same transcript as
the AI guide's messages.

Errors: `404 ROOM_NOT_FOUND`, `422 MEMBER_NOT_RESOLVED`, `422 VALIDATION_ERROR`,
`503 DATABASE_ERROR`.

### Reading live data directly

Writes always go through the endpoints above. For reads and live updates the frontend may
use Supabase directly with the anon key (see `docs/SUPABASE_ACCESS_BOUNDARY.md`):
`party_rooms`, `room_members`, `guests`, `characters`, `trips`, `messages`,
`vote_sessions`, `votes`, `selections`, `itinerary_versions`, `feedback`.
`travel_preferences` and `agent_runs` are backend-only.

These stream changes over Realtime: `party_rooms` (watch `planningStage` to move every
screen to the next stage together), `room_members` (roster and `stageReady`), `trips`
(watch `status`), `messages`, `vote_sessions`, `votes`, `selections`,
`itinerary_versions`, and `feedback`. `guests` and `characters` are readable but do not
stream; re-read them when the roster changes.

### Stage readiness

`room_members.stage_ready` drives "waiting for X of N party members". The backend is its
only writer:

| Stage | A member becomes ready when they… |
|---|---|
| SETUP | save their preferences (`PUT …/preferences`) |
| DISCOVER, LOGISTICS | cast a vote that does not close it (`POST /votes/{id}/cast`) |
| REFINE | give feedback on the version under review (`POST /trips/{tripId}/feedback`) |
| BUILD, WRAP | (not used) |

Whenever the room's `planningStage` changes, every member's `stageReady` resets to
`false`, so each stage starts fresh. In REFINE it also resets when a refinement proposes a
new version (trip status `refinement_completed`), so each round of feedback starts fresh. The party usually moves on by itself (the last member
to submit or vote advances the trip), so the waiting count is for display, not a gate the
frontend enforces.

### Errors

Every error response has this body (never FastAPI's default `{ "detail": … }`):

```json
{ "error": { "code": "ROOM_NOT_FOUND", "message": "Room 'ABC123' not found." } }
```

Branch on `code`, not `message`. `message` is safe to log; it is not tuned for display.

| Status | `code` | Meaning |
|---|---|---|
| 404 | `ROOM_NOT_FOUND` | No room with that code. |
| 404 | `TRIP_NOT_FOUND` | No trip with that id. |
| 404 | `VOTE_SESSION_NOT_FOUND` | No vote session with that id. |
| 404 | `RUN_NOT_FOUND` | No AI run with that id. |
| 404 | `ITINERARY_VERSION_NOT_FOUND` | No itinerary version with that id on this trip. |
| 404 | `NO_APPROVED_ITINERARY` | Export requested before any version was approved. |
| 409 | `VERSION_NOT_PROPOSED` | That version is not the one under review. |
| 409 | `DUPLICATE_APPROVAL` | Another version of this trip is already approved. |
| 409 | `IDEMPOTENCY_KEY_CONFLICT` | Key already used for a different trip or run type. |
| 409 | `MEMBER_ALREADY_EXISTS` | Name taken in a race; retry the join. |
| 409 | `TRIP_DATES_LOCKED` | The dates cannot change now (flight locked, or a flight search is running). The message is safe to show. |
| 422 | `VALIDATION_ERROR` | Bad body or path; `message` names the fields. |
| 422 | `INVALID_DISPLAY_NAME` | Display name is blank. |
| 422 | `INVALID_BUDGET` | Budget is outside SGD 100–50,000. The message is safe to show the member. |
| 422 | `INVALID_TRIP_DATES` | Trip length or dates do not fit when the party is free. The message is safe to show. |
| 422 | `MEMBER_NOT_RESOLVED` | `memberId` is not a member of this room (or not the owner, when closing a vote). |
| 422 | `VOTE_SESSION_CLOSED` | The vote has already closed. |
| 422 | `VOTE_TIE_PENDING` | The vote is tied; the room owner must pick the winner (`break-tie`). |
| 422 | `INVALID_IDEMPOTENCY_KEY` | Idempotency key is blank or too long. |
| 500 | `ROOM_CODE_EXHAUSTED` | Could not find a free room code; retry. |
| 500 | `INTERNAL_ERROR` | Unexpected server error. |
| 503 | `DATABASE_ERROR` | Database unavailable or failed; retry later. |

## Chat Message Flow

A room message has a stable envelope:
- `id`, `roomId`, `createdAt`
- `senderType`: `"user" | "ai"`
- `senderId`: room member id (`room_members.id`), or null for AI
- `kind`: `"text" | "recommendation" | "vote" | "summary"`
- `content`: shape depends on `kind` (see below)

Flow:
1. User sends a text message (`POST /rooms/{roomCode}/messages`) → persisted to Supabase →
   broadcast via Realtime.
2. Backend AI produces messages (any `kind`) → persisted → broadcast via Realtime.
3. Clients render new messages from the Realtime stream.

## AI Response Structure

An AI turn returns one or more messages sharing the envelope above. Common fields in
`content` for AI text:
- `text`: NPC dialogue string.
- `options?`: array of `{ id, label }` for quick single-choice replies.
- `stage?`: current planning stage indicator (drives progress UI).
- `progress?`: `true` on the single "the guide is thinking" message an AI run posts when it
  starts. Render it as a transient in-progress state, not a permanent chat line; it is
  superseded by the run's output or failure message.

## Recommendation Response Structure

`kind: "recommendation"` content. Used in DISCOVER (destinations) and LOGISTICS (flights):
- `title`: short heading.
- `category?`: `"destination" | "flight"` — which stage this set belongs to.
- `items`: array of 3–5 recommendation entries, each:
  - `id`, `title`
  - `description`: one sentence shown on the card (never empty from the backend).
  - `imageUrl?` / `spriteKey?`
  - `meta`: card details. The backend always sends these five keys (the frontend also
    accepts the aliases in brackets):

    | Key | Type | Shown as | Aliases |
    | --- | --- | --- | --- |
    | `score` | number 0–100 | "FIT {n}/100" badge | `fit`, `fitScore`, `match` |
    | `whyThisFits` | string | why it suits the party (falls back to `description`) | `why`, `reason` |
    | `tags` | string[] (≤ 4 short labels) | chips | `highlights`, `pros` |
    | `tradeOff` | string | the main downside | `tradeoff`, `con`, `warning` |
    | `details` | string | expanded "full details" text | `fullDetails`, `longDescription` |

- `prompt?`: optional follow-up question for the party.

**Destinations.** One LLM call builds the whole set from the party's preferences (prompt
text in `backend/app/agents/prompts/discovery_*.md`). Places a member typed themselves
always come first; trip types such as "Asia" or "Beach Escape" guide the suggestions but
never become cards. Destination `meta` also carries:

| Key | Type | Meaning |
| --- | --- | --- |
| `pick` | string | Badge: `"Best fit"` (exactly one, the top score), `"Budget pick"`, `"Hidden gem"`, `"Wildcard"`; fallback cards use `"Party pick"` (a place the party named) or `"Guide's pick"` |
| `bestFor` | string[] | Display names of the members it suits best (may be empty) |
| `estimatedDailyCostSgd` | number \| null | Rough cost per person per day in SGD for stay, food and local transport (no flights, no paid activities) |
| `scoreBreakdown` | object \| null | `{ preferences, budget, season, tripLength }`, each 0–10 |
| `tripDays` | number \| null | How long this trip is: the AI's suggested length for this place, checked by the backend |
| `tripStart` / `tripEnd` | ISO date \| null | The trip's dates, inside when the whole party is free |
| `whyThisLong` | string \| null | Why that length (and a note if it was shortened) |

**Trip length.** Members' dates say when they are *free*, not how long the trip is. The
AI suggests a length per destination; the backend keeps it within 2–14 days and within the
days the party is free, shortens it if the stay would use more than 60% of a hard budget,
and picks dates that cover the most weekend days (earliest first on a tie; a trip can
start as soon as tomorrow). The vote is on the destination *with* its trip plan; the
locked selection keeps `tripDays` / `tripStart` / `tripEnd`, and the flight search, budget
and itinerary all use them. Cards without a plan get a default 5-day trip.

`score` is computed by the backend from `scoreBreakdown`: 10 × (0.4 × preferences + 0.2 ×
budget + 0.2 × season + 0.2 × tripLength). Suggestions whose cost for the trip clearly
exceeds the party's budget are dropped while enough options remain, and at most two cards
come from one country. If the LLM is unavailable, the backend still fills every key: places
matching the party's trip types, `score` 85 for a place the party named and 70 otherwise,
plain copy, and `scoreBreakdown`/`estimatedDailyCostSgd` set to `null`.

```json
{
  "id": "penang--malaysia",
  "title": "Penang, Malaysia",
  "description": "An island blending UNESCO-listed heritage streets with sandy coves and legendary street hawkers.",
  "meta": {
    "score": 88,
    "whyThisFits": "Both Gerald and Priya prioritise food, which Penang delivers with dishes like char kway teow…",
    "tags": ["Street Food", "Coastal Trails", "Night Markets", "Heritage"],
    "tradeOff": "Beaches are better for sunsets than swimming; take a boat to Teluk Kampi for cleaner sands.",
    "details": "Mid-October brings brief afternoon showers… Daily expenses average around 40 to 60 SGD…",
    "pick": "Best fit",
    "bestFor": ["Gerald", "Priya"],
    "estimatedDailyCostSgd": 50,
    "scoreBreakdown": { "preferences": 9, "budget": 9, "season": 7, "tripLength": 10 }
  }
}
```

**Flights.** Built from the flight tool's facts (no LLM). `meta` keeps the factual keys
(`flight_id`, `carrier`, `flight_number`, `origin`, `destination`, `depart_at`,
`arrive_at`, `price`, `duration_minutes`, `stops`, `return_at`, `return_arrive_at`) and
adds the five card keys:
- `score`: value for money against the other options shown: 95, minus up to 30 for being
  the priciest, up to 15 for being the slowest, and 8 per stop.
- `tags`: `[price, airline, duration, stops]`, e.g. `["SGD 980", "Singapore Airlines",
  "6h 45m", "Direct"]`.
- `whyThisFits`: e.g. "The cheapest option for the party."; `tradeOff`: e.g. "SGD 380 more
  than the cheapest option."
- `details`: carrier, route, times, duration, stops and whether the price is round trip.

The frontend renders destination and flight option sets with the same recommendation +
comparison UI, keyed off `category`.

## Voting Structure

Voting has a session plus per-member votes.

Vote session (`kind: "vote"` content or dedicated object):
- `voteSessionId`, `roomId`, `question`
- `options`: array of `{ id, label, count }`
- `status`: `"open" | "closed"`
- `tie_pending`, `tie_option_ids`, `category`: set while a tie waits for the room owner
  (see "Ties" under HTTP API).

Cast a vote:
- Input: `{ voteSessionId, optionId, memberId }`.
- One vote per member per session; re-voting replaces the previous choice.
- Live counts update via Realtime.

When a vote resolves, the locked choice is stored as a selection
(`{ roomId, kind: "destination" | "flight", data, voteSessionId? }`), one per kind per room.
AI outputs are proposals; the party's decision determines the selection.

## Itinerary Format

The trip plan (rendered as quest log in BUILD/REFINE and adventure summary in WRAP). An
itinerary object:
- `tripId`, `roomId`, `title`, `summary`
- `destination`: `{ name, country? }`
- `dates?`: `{ start, end }`
- `days`: array of day plans, each:
  - `day`: number
  - `date?`
  - `items`: ordered activities, each `{ id, time?, title, description?, location?, tags?,
    cost? }`. `id` is stable across versions so feedback can target a specific activity.
    `cost` is the AI's rough cost per person in SGD for a paid activity (0 if free, absent
    if unknown); prices never appear in the text.
- `map?`: points array `{ label, lat, lng }` for the travel map view.

The journal, quest log, timeline, and map are all derived from this single object.

## Itinerary Versioning

BUILD produces version 1; REFINE appends new versions (history is never overwritten). A
version wraps the itinerary:
- `id`: itinerary version id.
- `version`: incrementing integer, unique per trip.
- `source`: `"build" | "refine"`.
- `status`: `"proposed" | "approved" | "rejected" | "superseded"`.
- `itinerary`: the itinerary object above.
- `changeSummary?`: short note of what changed vs. the prior version (REFINE only).

The UI can list versions and step through/compare them. At most one version per trip is
`approved`; the version under review is the latest `proposed` one.

## Feedback & Refinement (REFINE)

Feedback entry (submitted by a party member):
- Input: `{ tripId, itineraryVersionId, memberId, target, comment }`
  - `target`: what the feedback applies to: `{ day?, itemId?, section? }` with at least
    `day` or `itemId`.
  - `comment`: the party member's comment or suggested change.
- `status`: `"open" | "addressed"`.

Refinement result (from the AI):
- An analysis `text`/`summary` message: conflicts identified and compromises proposed.
- A new itinerary version (see above) with `source: "refine"`, `status: "proposed"`, and a
  `changeSummary`. The version it replaces becomes `superseded`.
- Decision: `{ tripId, itineraryVersionId, decision: "approve" | "reject" }`, made by the
  room owner. Approving marks the version `approved` and moves the trip to WRAP. See "HTTP
  API" for the feedback, decision, and export endpoints.

## AI Runs

Each AI operation (discovery, logistics, itinerary, refinement) is tracked as a run:
- `{ id, tripId, runType, status, baseVersion, resultVersionId?, error? }`
  - `runType`: `"discovery" | "logistics" | "itinerary" | "refinement" | "tiebreak"`.
  - `status`: `"pending" | "running" | "completed" | "failed"`.
  - `baseVersion`: the itinerary version number the run started from (0 = none yet).
- Requests that trigger a run may send an `idempotencyKey`; repeating a request with the
  same key returns the existing run instead of starting a duplicate.

## Stage & State

Every planning surface reflects where the party is:
- `stage`: `"setup" | "discover" | "logistics" | "build" | "refine" | "wrap"` — the active
  stage (also carried on AI `text` content).
- `state`: the application-state progression (see `system-workflow.md`) that gates
  transitions and drives progress UI. Stored as the trip status, one of:
  `"trip_created" | "group_formed" | "preferences_collected" | "destination_selected" |
  "flight_selected" | "itinerary_generated" | "feedback_collected" |
  "refinement_completed" | "trip_approved" | "trip_exported"`.

## Export (WRAP)

Finalisation (`POST /trips/{tripId}/export`) returns the approved itinerary version together
with the locked destination, flight, and party: everything the WRAP screen shows and
shares.
