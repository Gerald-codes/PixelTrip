# Supabase Architecture

Supabase is the shared data platform for the group travel planner: PostgreSQL, Realtime,
Storage, and Row Level Security. **Supabase Auth is not used** — there is no sign-up,
sign-in, password, PIN, token, or logout flow.

This project uses a **guest/demo trust model**. A room participant is identified by the
combination of the room and their normalized display name. If the same display name is
entered again in the same room, the existing room member is resumed.

The schema lives in `supabase/migrations/`.

## Guest Identity Model

Identity is room-scoped:

`room + normalized display name -> room member`

Example:

- Room `ABC123` + `Gerald` -> existing Gerald member, if present.
- Room `ABC123` + `gerald` -> the same member.
- Room `XYZ789` + `Gerald` -> a different room member.

The client does **not** generate the guest/member UUID as the source of identity. UUIDs
are generated by PostgreSQL/backend when records are created.

Join flow:

1. User enters a room code and display name.
2. The service resolves the room from the room code.
3. The display name is trimmed and normalized for matching.
4. The service searches `room_members` for `(room_id, normalized_name)`.
5. If found, return the existing member and associated guest/character.
6. If not found, create the guest, room member, character, and preference record.
7. The frontend may cache `room_id`, `member_id`, `guest_id`, and `display_name` in local
   storage for convenience, but cached values are not an authentication mechanism.

Impersonation is intentionally not prevented for the MVP. Anyone who knows the room code
and an existing display name can resume that member. Do not store sensitive personal data.

## Supabase Responsibilities

- **Guest profiles** — lightweight display/avatar records; no authentication credentials.
- **Room-scoped membership** — member identity, display name, role, and room association.
- **Pixel characters** — avatar and appearance selections for a room member.
- **Travel preferences** — room/trip-specific availability, budget, interests, travel
  style, destination interests, activities, and hard constraints.
- **Party rooms** — shared planning rooms identified by a unique room code.
- **Messages** — user and AI/NPC messages within a room.
- **Votes** — vote sessions and per-member votes for decisions such as destinations and
  flights.
- **Selections** — locked-in destination and flight/travel choices.
- **Trips** — the active trip associated with a planning room.
- **Itineraries & versions** — generated plans and revised versions from REFINE.
- **Feedback** — member comments and requested changes during REFINE.
- **Stage & state** — active planning stage and application-state progression.
- **Agent runs** — AI workflow execution metadata, version base, status, and idempotency.
- **Realtime updates** — live sync of members, messages, votes, selections, itinerary
  versions, feedback, and planning progress.
- **Storage** — sprite assets and optional uploaded imagery.

## Recommended Database Entities

All primary keys are UUIDs generated by PostgreSQL. Tables include `created_at`; mutable
tables also include `updated_at`.

### `guests`

Lightweight profile record retained because the existing frontend architecture models
avatars/characters around a guest.

- `id`
- `display_name`
- `avatar_url?`

A guest is **not** authenticated. Room membership, not `guests.id`, determines the
room-scoped identity used by the application.

### `party_rooms`

- `id`
- `room_code` — unique shareable code
- `name`
- `status`
- `planning_stage`

The room owner is represented by a `room_members.role = "owner"` membership rather than
an authentication account.

### `room_members`

- `id`
- `room_id -> party_rooms.id`
- `guest_id -> guests.id`
- `display_name`
- `normalized_name`
- `role` — `"owner" | "member"`

`UNIQUE(room_id, normalized_name)` implements the MVP identity rule.

There should be at most one owner membership per room.

### `characters`

- `id`
- `member_id -> room_members.id`
- `appearance` (`jsonb`)
- `sprite_key`

A character belongs to a room member rather than directly defining identity.

### `travel_preferences`

- `id`
- `member_id -> room_members.id`
- `available_dates` (`jsonb`)
- `destinations` (`jsonb`)
- `travel_style`
- `budget`
- `interests` (`jsonb`)
- `activities` (`jsonb`)
- `hard_constraints` (`jsonb`)

Preferences are room/trip scoped. This allows the same display name in different trips to
have different budgets, availability, interests, and constraints.

### `messages`

- `id`
- `room_id -> party_rooms.id`
- `sender_type` — `"user" | "ai"`
- `sender_member_id -> room_members.id`, nullable for AI
- `kind` — `"text" | "recommendation" | "vote" | "summary"`
- `content` (`jsonb`)

### `vote_sessions`

- `id`
- `room_id -> party_rooms.id`
- `message_id -> messages.id`, optional
- `question`
- `options` (`jsonb`)
- `status` — `"open" | "closed"`

### `votes`

- `id`
- `vote_session_id -> vote_sessions.id`
- `member_id -> room_members.id`
- `option_id`

`UNIQUE(vote_session_id, member_id)` ensures one active choice per member. Re-voting
updates the existing row.

### `selections`

- `id`
- `room_id -> party_rooms.id`
- `kind` — `"destination" | "flight"`
- `data` (`jsonb`)
- `vote_session_id -> vote_sessions.id`, optional

Only one locked selection of each kind should exist per room.

### `trips`

- `id`
- `room_id -> party_rooms.id`
- `title`
- `summary`
- `status`

The room has one active trip. The generated plan lives in `itinerary_versions`.

### `itinerary_versions`

- `id`
- `trip_id -> trips.id`
- `version`
- `source` — `"build" | "refine"`
- `status` — `"proposed" | "approved" | "rejected" | "superseded"`
- `itinerary` (`jsonb`)
- `change_summary?`

`UNIQUE(trip_id, version)` gives stable version numbering. Only one approved version
should exist per trip.

Activities inside the itinerary JSON should have stable `id` values so feedback can
target a specific activity.

### `feedback`

- `id`
- `trip_id -> trips.id`
- `itinerary_version_id -> itinerary_versions.id`
- `member_id -> room_members.id`
- `target` (`jsonb`)
- `comment`
- `status` — `"open" | "addressed"`

A structured `target` can identify a day, activity, or itinerary section.

### `agent_runs`

- `id`
- `trip_id -> trips.id`
- `created_by_member_id -> room_members.id`, optional
- `run_type`
- `base_version`
- `status` — `"pending" | "running" | "completed" | "failed"`
- `idempotency_key`, optional and unique
- `result_version_id -> itinerary_versions.id`, optional
- `error`, optional

This table coordinates AI runs and helps prevent duplicate generation requests.

## Relationships

- `party_rooms 1—N room_members`
- `guests 1—N room_members`
- `room_members 1—0..1 characters`
- `room_members 1—0..1 travel_preferences`
- `party_rooms 1—N messages`
- `party_rooms 1—N vote_sessions`
- `vote_sessions 1—N votes`
- `room_members 1—N votes`
- `party_rooms 1—N selections`
- `party_rooms 1—1 active trip`
- `trips 1—N itinerary_versions`
- `trips 1—N feedback`
- `room_members 1—N feedback`
- `trips 1—N agent_runs`

## Row Level Security

Because Supabase Auth is not used, RLS cannot establish a trustworthy user identity with
`auth.uid()`.

This is intentionally a **guest/demo trust model**:

- Enable RLS on application tables.
- Client identity fields such as `member_id` are self-asserted and must not be treated as
  secure authorization.
- The application may allow the anon client the minimum room-oriented read/realtime access
  needed by the MVP.
- Important mutations and AI-authored records should preferably pass through the FastAPI
  service, which uses trusted server-side Supabase credentials.
- Never expose the Supabase service-role key to the frontend.
- Do not store sensitive personal data.
- If real per-user security is required later, introduce Supabase Auth and replace these
  trust-model policies.

RLS in this MVP provides database access boundaries, not proof that a display name belongs
to a particular human.

## Realtime

Subscribe per room, for example `room:{room_id}`.

Recommended Realtime-tracked data:

- `room_members`
- `messages`
- `vote_sessions`
- `votes`
- `selections`
- `itinerary_versions`
- `feedback`
- `party_rooms.planning_stage`
- `trips.status`

Supabase Realtime Presence may be used to show who is currently online. Presence is
ephemeral and should not be used as the source of membership identity.

## Storage

Use a bucket for pixel/sprite assets and optional user-uploaded imagery.

Store references using `characters.sprite_key` and `guests.avatar_url`. Do not place
credentials or sensitive information in public storage.

## Access Boundaries

UI components do not query Supabase directly.

- `src/services` owns application-facing data operations.
- `src/lib` owns the Supabase client/configuration.
- FastAPI owns AI orchestration and important server-side mutations.
- LangGraph does not become the source of truth for trip data; it loads current trip
  context from Supabase and returns proposals/results to be persisted.

Conceptually:

```text
React UI
   |
   v
Frontend Service Layer
   |---------------------> Supabase (reads / Realtime where appropriate)
   |
   +---------------------> FastAPI
                              |
                              +----> Supabase
                              |
                              +----> LangGraph / tools
```

## Design Rules

1. `room + normalized display name` is the MVP member identity rule.
2. UUIDs are generated by the database/backend, not used as client-created identity.
3. Preferences belong to `room_members`, not globally to a character.
4. Votes and feedback reference `room_members.id`.
5. AI outputs are proposals; human decisions determine locked selections and approval.
6. Itinerary revisions append versions rather than overwriting history.
7. LangGraph workflow/checkpoint state is separate from canonical Supabase trip data.
8. No authentication/security guarantees should be implied by the guest identity model.
